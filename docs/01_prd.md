# PRD — moonx

> **地方で地元ビジネスを始めたい人が、自己分析からアイデア検証、ビジネスプランまでを、スマホとWebで迷わず進められる起業検討アプリ。**

- 入力: `docs/concept.md`（Phase 0）、`docs/design-spec.md`（画面・UX の正）、`docs/02-01_system-design-doc.md`（1章 Goal / Non-Goal）
- この文書が正として持つもの: 目的・対象ユーザー・ユーザーストーリーと優先度・KPI・スコープ外
- 画面の存在・目的・レイアウト・状態は `design-spec.md` が正。技術とデータモデルは `02-01_system-design-doc.md` が正。ここには転記せず、画面番号（例: 13 検証ホーム）と節番号で参照する
- 用語は design-spec 1.4 に合わせる

## 1. 概要

moonx は、地方で店舗や実業などの地元ビジネスを始めたい人のための起業検討アプリ。「自己分析 → アイデア検証 → ビジネスプラン」の3工程を、スマホと Web の両方で進められる。

- BCDX が Google Drive のテンプレートで回している手順を、そのままアプリにする（design-spec 1.1）
- アプリが担うのは、入力・その場の計算・足りないものの見える化・プランへの引き継ぎ。AI はアプリに組み込まず、外部の AI との往復だけを支える
- 点数は付けない。足りないものを状態として示す
- 初期リリースは design-spec 1.2 のフル機能を、招待制で BCDX だけに出す（試運転）。設計は一般公開を前提にし、誰でも登録できる受付は一般公開のときに開く

主な流れは design-spec 2.3 のとおり。中心はコアフロー「アイデアを検証して判定する」（6 → M1 → 13 → 11・14〜18 → 19）。

## 2. 背景と目的

### 背景

- BCDX は「自己分析 → アイデア検証 → ビジネスプラン」の手順を、Google Docs / Sheets のテンプレートで回している
- 汎用ツールのため、次の3つの負担がある（詳細は design-spec 1.1）
  - **工程間の転記と全体把握**: 検証の数字や顧客・課題をプランへ手で写している。複数アイデア・複数メンバーの進み具合を一覧できない
  - **検証の抜け漏れ**: 必須の確認項目と Fact / Assumption / Unknown の区別が、どこまで済んだか分からない
  - **スマホでの入力**: 結合セルの多い表や長いドキュメントを、スマホから埋めにくい
- この手順は、地方で起業を考える人にも役立つ。社内専用にせず、最初から一般向けとして設計する
- 現行の手順には、守りたい原則がある。恣意的なスコアで選ばない。勝者を早く決めない。Proceed は「プランに進める価値がある」という意味で、立ち上げの承認ではない。検証の根拠を残す。起業を答えとして押し付けない

### 目的

1. **BCDX が Drive での運用を丸ごと置き換える。** 新しい検討はすべて moonx で始め、moonx で判定し、プランにする
2. **足りないものを見えるようにする。** 確認項目6つの状態と F/A/U の内訳を示し、判定を理由とともに残す。点数は付けない
3. **転記をなくす。** 数字の正を検証の1か所に置き、プランは検証を参照する
4. **スマホの空き時間でも進められるようにする。** スマホで1問ずつ答え、続きを Web で開ける
5. **BCDX で使い込んだまま一般公開する。** 地方で起業を考える人の役に立てる。公開は、地元への貢献と実績づくりを兼ねる

## 4. 主要機能（ユーザーストーリー）

優先度は、初期リリースの中で作る順番と、コアフローに要るかどうかを示す。初期リリースのスコープはすべてのストーリーを含む（design-spec 1.2）。

- **Must**: コアフロー「アイデアを検証して判定する」（design-spec 2.3）と、それが依存するもの（招待・ログイン・共通の入力部品）。最初に作る
- **Should**: コアフローの次に作る。3工程をつなぐもの（自己分析・プラン）と、チームで使うための仕組み
- **Could**: 最後に作る。実行管理・Pitch Deck・運営の仕上げ

括弧内は design-spec の画面番号。画面の中身はそちらを見る。

## 5. 成功指標（KPI）

- 試運転（招待制・BCDX のみ）と一般公開で、指標と目標を分ける
- 数字は、アプリが保存しているデータ（System Design Doc のデータモデル。もとは design-spec 7章）か、簡単な手作業の件数から出す
- 集計は件数と割合だけにし、回答の中身は読まない（運営者は中身を見ない。design-spec 2.1）。集計は System Design Doc 11章の KPI 用の SQL（件数だけを数える）で、運営者が月に1回行う
- アイデアの良し悪しを測る指標は置かない。測るのは使われ方と検討の進め方だけ（点数を付けない原則。design-spec 1.3）

### 5.1 試運転（招待制・BCDX のみ。開始から3か月）

| # | 指標 | 目標 | 測定方法 |
|---|------|------|---------|
| K-01 | Drive の既存データの入れ直し | 開始から2週間以内に、自己分析1件と記入済みの検証1件を moonx に入れ終える | moonx に該当の自己分析とアイデアがあるかを確かめる |
| K-02 | 新しい検討が moonx で始まる（Drive のテンプレートの置き換え） | 開始1か月後から、Drive に新しい自己分析・検証・プランのファイルが0件。新しいアイデアは 100% moonx で作られる | Drive の BCDX フォルダの新しいファイルを月に1回手で数え、moonx のアイデアの作成数と並べる |
| K-03 | 自己分析の完了と共有 | 開始から1か月以内に、BCDX の Owner / Member 全員が完了し、BCDX のワークスペースに共有する | 自己分析の状態（完了）と共有先を数える |
| K-04 | 判定の前に確認項目6つの状態が分かっている | Proceed の判定の 80% 以上で、記録の時点で「未着手」の確認項目が0 | 決定ログに残る、その時点の不足項目のスナップショットを数える |
| K-05 | 判定が理由とともに残る | 作成から4週間以上たったアイデア（アーカイブを除く）の 70% 以上に、判定が1件以上ある | 決定ログの判定をアイデアごとに数える（理由は記録に必須なので、記録された判定はすべて理由を持つ） |
| K-06 | Proceed からプランへの引き継ぎ | Proceed にしたアイデアの 100% で、プランを moonx で作る | Proceed の判定の数と、その判定から作ったプランの数を比べる |
| K-07 | 週ごとに使うメンバー | 各週、BCDX の Owner / Member の 70% 以上が記録を残す | 週ごとに、変更履歴・コメント・決定ログの記録者を数える |
| K-08 | スマホからの入力 | 回答の保存の 30% 以上がスマホのアプリから | 変更履歴の入力元（`change_history.client` = web / ios / android。System Design Doc 6.3）で数える |
| K-09 | 外部の AI との往復 | 試運転中に、Owner / Member の半数以上が AI 取り込みで1回以上回答を反映する | 変更履歴のうち、変更元が AI 取り込みのものを記録者ごとに数える |
| K-10 | アドバイザーの関わり | Viewer を招待したとき、その半数以上が月に1回以上コメントする | Viewer のロールの人が書いたコメントを月ごとに数える |

## 6. スコープ外

初期リリースで作らないもの。design-spec 1.2 / 9.2 / 9.4 と System Design Doc 1章 Non-Goal に合わせる。

| 項目 | 理由 | 見直す時期 |
|------|------|-----------|
| アプリへの AI の組み込み（AI の呼び出し・AI による提案や評価） | 入力・計算・進み具合の見える化に集中する。考えを深めるのは外部の AI との往復（24・25）で支える | 予定なし（プロダクト方針） |
| アイデアの点数・ランキング・判定順の並べ替え | 「恣意的なスコアで選ばない」「勝者を早く決めない」原則（design-spec 1.3） | 予定なし（原則） |
| 判定・Go / No-Go の投票や承認 | Member 以上なら誰でも記録でき、誰が・いつ・なぜを決定ログに残す（design-spec 2.1） | 予定なし |
| プッシュ通知・メール通知 | 通知はアプリ内（8）だけ。メールは招待とパスワード再設定だけ送る（認証に必要な連絡で、通知とは別） | メール通知は一般公開のときに検討する（9.2）。プッシュ通知は予定なし |
| 通知の設定（種類ごとのオン / オフ） | 初期は通知の種類が4つで、アプリ内だけ | 拡張候補（9.4） |
| 誰でも登録できる受付 | 初期リリースは招待制で、BCDX だけで試運転する | 一般公開の時期と条件を決めるとき（9.2） |
| Google Drive からの取り込み・同期・書き出し | 既存データは2件だけで、手で入れ直す | 予定なし（決定済み。9.4） |
| 決済・課金 | 収益化は保留で、当面は無料を前提にする | 収益化の有無と方式を決めるとき（9.2） |
| UI の多言語化 | 初期は英語だけ。多言語化できる作りは残す | 一般公開の利用者の言語を見て決める（9.2） |
| 回答の翻訳 | 回答は自由な言語で書ける。アプリは翻訳しない（design-spec 1.2） | 予定なし |
| 複数通貨の換算 | 通貨はワークスペースごとに1つ（既定 PHP）。通貨を変えても金額は換算しない | 拡張候補（9.4） |
| アイデア・プラン・ワークスペースの削除 | 初期リリースはアーカイブだけ。アーカイブで一覧とダッシュボードから隠せる（アカウントの削除はストアの規則で必須のため作る。C-11） | 拡張候補（9.4） |
| リアルタイムの共同編集（カーソルの共有・即時反映） | 項目ごとの自動保存と、衝突したときの確認で足りる（design-spec 6.0.2） | 同時編集の衝突が多いと分かったとき |
| オフラインでの閲覧 | 保存できなかった入力を再送するだけにする（design-spec 6.0.2） | 予定なし |
| 運営者がワークスペースの中身を見る機能 | 運営者に見えるのは件数や最終利用日などの利用状況だけ（design-spec 2.1） | 予定なし |
| 運営者が他のユーザーを運営者にする機能 | 最初の運営者は初期設定で1人にする（design-spec 9.2 の既定案） | 9.2 で方針を確定するとき |
| プランの版どうしの差分表示 | 項目ごとの差分は変更履歴（PNL-2）で見られる | 拡張候補（9.4） |
| 決定ログや一覧の CSV 書き出し | 初期はアプリの中で振り返れれば足りる | 拡張候補（9.4） |
| Pitch Deck のスライドの選択・並べ替え・直接編集 | Pitch Deck はプランから毎回作り、別の正にしない（design-spec 3.5） | 選択・並べ替えは拡張候補（9.4）。直接編集は予定なし |
| 調査ログの添付ファイル（写真など） | 根拠は調査ログの記述と URL で残す | 拡張候補（9.4） |
| 立ち上げ後の日々の業務（会計・在庫・販売など）の管理 | moonx が扱うのは、検討から立ち上げ準備まで（工程は検証 / プラン / 立ち上げ準備。design-spec 1.4） | 予定なし |
